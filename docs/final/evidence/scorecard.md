# The evolution scorecard

**What this is.** How we decide whether the *next* version of this pipeline is
better than the current one. A rubric, applied to itself, with numbers — and with
a recorded case where it said no.

**Every number below came from a command.** The command is named beside it. The
raw data is `scorecard-baseline.json` in this directory, regenerated by:

```bash
.venv-main/bin/python scripts/measure_scorecard.py --runs 10 --require-real-scanners
```

**Baseline commit `9b2b1ee`, measured 2026-08-28T05:12:28+0300.** Measured before
Lanes A, B, C and E land, deliberately: this row describes a system that is about
to change, and once it has changed the baseline is unrecoverable.

---

## 1 · The dimensions, and why these seven

A dimension earns its place by being something this system can actually **move**.
Lines of code, number of agents and model size are excluded — they cannot be moved
in a direction that matters, and a scorecard that tracks them rewards the wrong
work.

| # | Dimension | What it means | Direction |
|---|---|---|---|
| 1 | **block correctness** | poisoned runs that blocked / poisoned runs | higher |
| 2 | **false-block rate** | clean runs wrongly blocked / clean runs | lower |
| 3 | **time to merge** | ticket opened → change merged | lower |
| 4 | **cost per merged change** | model + compute + human minutes | lower |
| 5 | **human touches** | decisions a run demands of a person | lower, with a floor |
| 6 | **agent-attributable rework** | revisions caused by an agent misreading the ticket | lower |
| 7 | **escaped defects** | things that shipped and should not have | lower |

Two of these have a **floor rather than a target**, and that distinction is the
scorecard's whole character:

- **Human touches must not reach zero.** Three gates requiring a named reviewer
  are the product. A release that reduced human touches to zero would have deleted
  the feature.
- **Block correctness must never fall.** See §3.

## 2 · The baseline row, measured today

### Measured on this machine

| Dimension | Baseline | How |
|---|---|---|
| **block correctness** | **1.0** (10 / 10) | 10 poisoned runs, every one ended `blocked` |
| **false-block rate** | **0.0** (0 / 10) | 10 clean runs, every one ended `promoted` |
| **human touches** | **1** poisoned · **3** clean | `len(RunState.decisions)`, median of 10 each |
| **agent-attributable rework** | **0** both arms | `RunState.revision_count`, median of 10 each |

Every poisoned run reported `scan_provenance: scanners` with findings on lines
**3 and 4** — the real-scanner pair. The fixture reports **4 and 5**. That
line-number set is the only field distinguishing a real scan from a JSON read:
`blocking=2`, the verdict, both rule names, the file, the tool and the severity are
produced identically by both paths, so a count proves nothing.

**`agent_rework` of 0 is a floor, not the live figure.** The measurement runs with
the model off, so the reviewer answers from `fixtures/review_result.json`, which
always approves. The live reviewer does withhold approval — run `32557597915` ran
four rounds and ended `failed` with security reporting `PASS`. Read this row as
"the harness contributes no rework of its own", and re-measure it against a live
model before quoting it as an agent-quality number.

**Human touches are only comparable within one outcome.** A blocked run demands
1 decision because the stages after the block never run; a promoted run demands 3.
Falling from 3 to 1 is not an improvement — it is a different ending.

### Not measured, with the reason

An honest gap beats an invented number: a gap invites the measurement and a number
ends it. Three dimensions have no source at this commit.

| Dimension | Why not | Command that closes it |
|---|---|---|
| **time to merge** | the local walk is 1.23–2.43 s while a real run is minutes, most of it a human deciding at a gate. Quoting the local figure would be wrong by two orders of magnitude in the flattering direction | `gh run list --workflow=run-pipeline.yml --limit 20 --json databaseId,createdAt,updatedAt,conclusion` |
| **cost per merged change** | **nothing records tokens.** `state.StageCost` declares `input_tokens` / `output_tokens` / `cached_tokens` and no code path writes them; `agentorg/common/llm.py` has no usage accounting at all | Lane E's instrumentation. | **escaped defects** | a rate over shipped changes, and the denominator is two merged PRs on the target repository | `gh pr list --repo mohamedsorour1998/auth-service --state merged --json number,mergedAt,title` |

**Zero escaped defects over two merges is not evidence of a low rate.** Report the
count and the denominator; never the ratio.

### The conditions, which are part of the numbers

`CLAUDE.md` records 116.88 s → 149.68 s → 102.83 s for one unchanged test
snapshot, purely load-dependent. So a measurement is a number **plus** its
conditions and spread.

| Condition | Value |
|---|---|
| Scanner mode | REAL-SCANNER — all three binaries on PATH |
| Regime | `OFFLINE=true`, `LLM_DISABLED=true`, no GitHub token, offline workspace redirected to a temp dir |
| Walk time, poisoned | 1.233614 – 1.756955 s (median 1.368313, n=10) |
| Walk time, clean | 1.436799 – 2.425226 s (median 1.560574, n=10) |

**Block correctness and the false-block rate reproduced exactly across three
independent 10-run batches** — 1.0 and 0.0 each time, at three different times of
day. The *timings* did not: the median poisoned walk moved from 1.241 s to
1.368 s between batches with no code change. That is the split this scorecard cares
about. A rate over discrete outcomes is stable and quotable as a point value; a
duration is not, and must always carry its spread.

**`tests/conftest.py`'s six autouse guards are pytest fixtures and do not bind to
a script.** `llm.available()` was measured **True** on this machine, so an
unguarded measurement run would have made a live billable Bedrock call per agent
per run. `measure_scorecard.py` forces the regime itself and refuses to proceed if
`llm.available()` is still true afterwards.

**The scanner cache had to be cleared per run, and finding that out changed the

`scan_provenance: scanners` and `blocking: 2`. The 25x timing gap is what exposed
it:

```

POISON-2 walk=0.0556   <- cache
POISON-3 walk=0.0591   <- cache
```

"10/10 blocked" would have been one measurement presented as ten, and no field in
the output would have said so. Every published row now clears the cache first, which
is why the walk times above are all ~1.2 s and none is ~0.05 s.

**Two scanner versions differ from the image's pins**, and the scorecard prints it
on every run:

| Tool | Local | Image pin | |
|---|---|---|---|
| gitleaks | 8.30.1 | 8.21.2 | differs |
| trivy | 0.74.0 | 0.74.0 | agrees |
| semgrep | 1.173.0 | 1.172.0 | differs |

The discriminator still comes out `{3, 4}` on 8.30.1, so it survives the gap — but
that is a measured fact about two specific versions, not a property of gitleaks.
A version that shifted the real lines onto `{4, 5}` would destroy the
discriminator while every provenance assertion kept passing. **Do not quote these
rows as evidence about the deployed container without checking that column.**

## 3 · The promotion rule

A change to this pipeline is accepted when **all five** hold. Four are gates; the
first is a veto.

### R1 · No regression on block correctness — the veto

> **Block correctness must not decrease. A release that ships faster while
> blocking less is a worse release, regardless of every other number.**

The gate is the product. This clause outranks the other four: a change that
improves time-to-merge, cost and human touches while dropping block correctness
from 1.0 to 0.9 is **rejected**, and no combination of the others buys it back.

Verified by:

```bash
.venv-main/bin/python scripts/measure_scorecard.py --runs 10 --require-real-scanners
.venv-main/bin/python -m pytest tests/test_block_determinism.py -q
```

`--require-real-scanners` is not optional for a published row. Without the
binaries the poisoned verdict comes from a JSON fixture, and **both paths report
`blocking=2`** — so a 1.0 measured in fixture mode is a claim about JSON
deserialisation wearing the same number.

### R2 · The false-block rate must not increase

A gate that blocks clean changes gets switched off by the first person it
inconveniences, and then it is theatre. Tightening the threshold to improve R1
must be paid for here, not banked.

### R3 · The four gates stay green, and the demo still runs

```bash
.venv-main/bin/python -m pytest -q                            # green
.venv-main/bin/python -m ruff check agentorg scripts tests    # exit 0
actionlint .github/workflows/*.yml                            # exit 0
cd infra/Terraform && terraform fmt -check -recursive         # exit 0
.venv-main/bin/python scripts/preflight.py                    # exit 0
```

Plus: a clean ticket merges and a poisoned ticket blocks with
`provenance: scanners` and exit 3.

### R4 · Every number in the claim comes from a committed command

`CLAUDE.md` rule 4, applied to the scorecard itself. A change whose benefit is
described but not measured is not evaluable, so it is not promotable. **This rule
has already caught the specification** — §5 quotes four reference counts and
records no command for them; three do not reproduce (see
`dependency-inventory.md`).

### R5 · Human touches do not fall below three on a promoted run

Three gates, three named reviewers. An "improvement" that removes a gate is a
feature deletion and must be argued as one, not shipped as an efficiency.

### What is deliberately NOT in the promotion rule

- **Test count.** It moves whenever anyone commits, and a rule that rewards it
  rewards writing tests that pin nothing — which this repository has done 19+
  times and measured.
- **Wall-clock suite time.** Load-dependent by a factor of 1.5 on one unchanged
  snapshot.
- **Model quality scores.** The shipping decision is not the model's; a better
  model does not make the gate better.

## 4 · A recorded rejection — the scorecard saying no

> A rubric that has never rejected anything is decoration. This project already
> learned that lesson about tests.

This is not a hypothetical. It is a change that **passed all four gates, was
merged, and was wrong** — and the test written to protect it *required* the defect.

### The change

Commit **`f29c5a4`** — *"feat(demo): one revision on a poisoned run, three on a
clean one"*, 2026-08-22 19:36.

A poisoned run cannot converge: the developer removes the credential, the safety
net puts it back, and the reviewer objects again. Four rounds of that reads on a
projector as an agent that cannot follow instructions. So `MAX_REVISION_LOOPS`
became `1` when poisoned and `3` otherwise:

```yaml
MAX_REVISION_LOOPS: ${{ inputs.poisoned == 'true' && '1' || '3' }}
```

Sound reasoning, real problem, correct intent.

### What was wrong

`poisoned` is declared `type: boolean`. In an **expression** context on a UI or
`gh workflow run` dispatch, `inputs.poisoned` is therefore a real boolean — and
`== 'true'` against a boolean is always **false**. Every run silently took the
clean branch.

MEASURED on run **`32585947588`**, the final verification run of the poisoned path:

```
POISONED: true
MAX_REVISION_LOOPS: 3        <- the CLEAN branch, on a poisoned run
```

### Why nothing caught it

Three tests read the workflow's text. One of them asserted the defect was
present:

```python
assert "== 'true'" in expression or '== "true"' in expression, (
    f"the cap compares `poisoned` against a boolean, not the string GitHub "
    f"actually sends, so the condition is always false: {expression}"
)
```

Read the failure message. It describes the bug **correctly** — comparing against a
boolean makes the condition always false — and then asserts the presence of the
expression that does exactly that. So the test **passed on the defect and would
have failed on the fix.**

The commit that introduced this also documented a RED step for this precise
mutation: *"comparing `poisoned` against a real boolean instead of the string
GitHub sends (condition always false, every run silently gets 3)"*. The mutation
was run. It failed the test as expected. And the shipped expression was the
mutation — because the comment, the test and the author all agreed with each other
about what GitHub does, and none of them had checked.

**Only the deployed run could tell.** Every local gate was green throughout: 1098
tests passing, ruff clean, actionlint clean.

### What the scorecard says

| Rule | Verdict |
|---|---|
| R1 block correctness | **not affected** — the verdict is computed once, after the loop, over a diff that always carries the key. Same block, same two findings, same lines |
| R2 false-block rate | not affected |
| R3 four gates | **passed — and that is the finding.** All four were green on the defect |
| R4 every number measured | **FAILED.** The claim "the poisoned run now uses a cap of 1" was never measured against the platform. The evidence was a workflow file read by a test, not a run |
| R5 human touches | not affected |

**Rejected under R4.** Not because the intent was wrong — the fix, `058d999`,
keeps the intent exactly — but because the *evidence* was a test reading the text
of the thing it was testing.

### The correction

Commit **`058d999`** — *"fix(demo): the revision cap compared a boolean to a
string, so it never applied"*, 2026-08-22 20:00, 24 minutes later.

```yaml
MAX_REVISION_LOOPS: ${{ (inputs.poisoned && inputs.poisoned != 'false') && '1' || '3' }}
```

A truthiness test that **also excludes the string `"false"`**, because both input
shapes are real: a REST dispatch — EventBridge, and every `gh api` call — sends
these inputs as JSON strings, and a non-empty `"false"` string is **truthy** to
GitHub. A bare `inputs.poisoned` would have sent clean API-triggered runs down the
poisoned branch: the same class of defect, in the other direction.

The three text-reading tests were replaced by four that **evaluate** the
expression the way the runner does, across both dispatch shapes, with a
deliberately narrow evaluator that **raises on any operator it was not written
for** — an evaluator that silently mishandles an operator is the same false
confidence one level up.

### The rule this produced

> **A workflow expression cannot be tested by reading the workflow.** The runner's
> type coercion *is* the behaviour. Where behaviour depends on a platform's
> evaluation, the test must evaluate.

And the more general one, which is why R4 exists:

> **When a comment and a test agree with each other and nobody checked either
> against the platform, the agreement is worthless.**

### Five more rejections on the record

Same shape, briefly, each a change that was made and then found wrong by
measurement rather than by review:

| Change | What measurement caught | Correction |
|---|---|---|

Fixed in `d237b32`. The token still needs rotating — deleting the artifacts removed the distribution channel, not the exposure |

### Two structural facts about this log

**There is no `git revert` in 222 commits** — measured, `git log --grep="^Revert"`
returns zero. Every correction is a forward fix, and a superseded claim is kept in
place rather than deleted: `0d229dc` retains a wrong 2-of-5 measurement marked
`[SUPERSEDED]` *"because the 2/5 is the evidence that the defect was real."* The
rejection log is written into the codebase, which is the only reason it is
recoverable at this distance.

**Every case above pasted four green gates.** In the two strongest — the revision
cap and the `promote` exemption — the test did not merely miss the defect, it
**enforced** it. The gates were not blind; they were aligned against the fix. That
is why R4 asks where a number came from rather than whether the suite is green.

## 6 · One finding for the integrator, not a scorecard row

**`tests/test_trigger_provenance.py::test_the_stage_records_the_trigger_onto_the_run_state`
fails in a git worktree and passes in the main checkout.** Measured at `9b2b1ee`
with **every Lane L file moved off disk**, so it is not caused by this lane:

```
1 failed, 1148 passed, 4 skipped
AssertionError: no state file for run <uuid>; this test cannot read what the
stage recorded
```

**The cause.** The test shells out to `scripts/run_stage.py plan` and then looks
for the state file in two places: its temp workspace, and `REPO_ROOT/runs`. The
subprocess writes to neither. Reproduced directly:

```
$ .venv-main/bin/python scripts/run_stage.py plan --ticket-id TRIGGER-1 ... --trigger issue
run_id=2cf87496-c37a-4529-a392-ec30c4f75eac
state=/Users/sorour/sorour/TheAgentOrg/runs/2cf87496-...state.json
```

That is the **main checkout's** `runs/`, not the worktree's. `gates._STATE_DIR` is
`Path(__file__).parent.parent / "runs"`, and in a subprocess `agentorg` resolves
through the editable install's finder — which points at the main checkout —
rather than from cwd. Imported in-process from the worktree, the same expression
correctly gives the worktree's path; the divergence appears only across a
subprocess boundary.

**Also measured: the test's `RUNS_DIR` env var is read by nothing.**
`grep -rn RUNS_DIR agentorg/ scripts/` returns no hits, so the knob the test sets
to redirect state has no effect. The `REPO_ROOT/runs` fallback is what makes it
pass in the main checkout — by finding a file written to the same directory for a
different reason.

**Not fixed here.** `tests/test_trigger_provenance.py` is not Lane L's file, and
the fix is a judgement about the seam rather than a typo: either `run_stage.py`
gains a real state-directory knob, or the test stops asserting across a
subprocess boundary whose module resolution it does not control. Handed to the
integrator, with the reproduction above.

**Why it matters beyond one red test.** Every lane in this phase works in a
worktree. A test that passes in the main checkout and fails in a worktree will be
read as "the lane broke it", and the lane will spend time proving otherwise — as
this one did.

### THE PHASE 4 REJECTION — "the queue replaces GitHub Actions", refused under R4

> A rubric that has never rejected anything is decoration. §4 records six rejections
> from before this phase; this is the one from **this** phase, and it is the claim the
> deck most wanted to make.

**The proposed claim.** Lane A built `agentorg/queue/` + `scripts/worker.py` — 1,931
lines plus 745 — to provide the sequencing, handoff, pause and isolation GitHub
Actions provides today, and CLAUDE.md records it verified end to end with no Actions
involved: a clean ticket reaches `promoted`, a poisoned one exits 3 with
`blocking=2`, a refusal exits 4. All true. The slide that wrote itself was *"the
pipeline no longer needs GitHub Actions."*

**Rejected. Three measurements, and each alone is sufficient.**

```
grep -icE 'queue|worker' .github/workflows/run-pipeline.yml     ->  1
grep -inE 'queue|worker' .github/workflows/run-pipeline.yml     ->
    145:# disk saying how it ended. Queue instead.
```

The **only** occurrence of either word in the deployed workflow is a **comment**, and
it is a comment about DynamoDB. Every one of the seven jobs still runs
`scripts/run_stage.py`. So the queue is not an alternative the deployed pipeline
selects — it is an alternative nothing selects.

```python
config.QUEUE_BACKEND with no env set : 'memory'
config.QUEUE_BACKEND_MEMORY          : 'memory'
equal                                : True
```

The durable backend is not the default, **and `config.py`'s own comment three lines
above says it is**: *"The durable backend is the deployed default and is chosen
deliberately, never inherited."* It is chosen deliberately in exactly one place —
`infra/selfhost/docker-compose.yml:134` — and inherited as `memory` everywhere else.
A comment and its own code disagreeing is §4's closing rule arriving inside one file.

```
grep -rn 'worker.py' .github/workflows/ infra/ --include='*.yml'
  ->  infra/selfhost/docker-compose.yml:170: command: ["python","scripts/worker.py","--forever"]

command -v docker  ->  /opt/homebrew/bin/docker
docker info        ->  NO DAEMON
```

The single caller of the worker is a compose file whose own header states that
`docker compose up` **has never been executed against it**, because there is no Docker
daemon on this machine. Re-measured here: the binary exists, the daemon does not.

| Rule | Verdict |
|---|---|
| R1 block correctness | **not affected.** 1.0 (10/10) at `d6165c8`, and the queue path's own verification blocked correctly too |
| R2 false-block rate | not affected |
| R3 four gates | **passed, and that is again the finding.** 1853 tests green, ruff/actionlint/terraform clean, preflight OK — on a capability nothing invokes |
| R4 every number from a committed command | **FAILED.** "Replaces Actions" is a claim about *what runs in production*, and the command that would support it (`grep worker.py .github/workflows/`) returns nothing |
| R5 human touches | not affected — and the queue's gate design is genuinely stronger, see below |

**Rejected under R4, and NOT under R1.** The distinction matters and is the reason
this is a rejection of a *claim* rather than of the *code*. The queue is correct: a
pause is a durable row, `claim` will not hand a `paused` job to a worker, and there is
no code path from `paused` to `ready` that does not carry a `HumanDecision` — which is
a stronger guarantee than an Actions Environment, since CLAUDE.md measures all three
of ours at `can_admins_bypass=True`. None of that is in dispute. What failed is the
tense: the deck wanted the present indicative for something in the subjunctive.

**What the deck says instead**, and it is the honest form of the same sentence:

> The pipeline's dependence on GitHub Actions is now a **choice rather than a
> constraint**. A second execution path exists, is tested, and blocks a poisoned
> ticket with no Actions involved. It is not what production runs today.

**This is the second pattern in CLAUDE.md — a correct answer nobody asks for —
arriving at the largest scale yet.** The four instances recorded there were single
