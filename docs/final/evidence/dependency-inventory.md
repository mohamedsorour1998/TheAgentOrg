# The dependency inventory

**What breaks this system if a third party changes, and how locked in are we.**
Specification §5.

**Every number below came from a command.** The raw data is
`dependency-inventory.json` in this directory, regenerated by:

```bash
.venv-main/bin/python scripts/measure_dependencies.py
```

Measured at commit `9b2b1ee`, 2026-08-28. Scope: `agentorg/` + `infra/`.
`tests/` is **excluded** on purpose — a token named in an assertion is not a
dependency of the product, and counting them would overstate lock-in.

---

## 1 · The three severities

A dependency's severity is not a judgement call. The test is what a replacement
costs.

| Severity | Test | Members |
|---|---|---|
| **Substitutable** | swap the binary; the interface is a subprocess and a JSON document | gitleaks, trivy, semgrep |
| **Seam-bound** | one adapter behind one function | GitHub, DynamoDB, EventBridge, Secrets Manager |
| **Load-bearing** | no seam, or the seam leads somewhere with no second implementation | the model provider, pydantic, AgentCore |

## 2 · Substitutable — the three scanners

**This is the only dependency class this project already handles correctly, and it
handles it better than most systems handle any of them.** Absent and broken get
*deliberately different answers*, because they are different faults.

| Tool | Image pin | Interface |
|---|---|---|
| gitleaks | 8.21.2 | `subprocess` → JSON report |
| trivy | 0.74.0 | `subprocess` → JSON report |
| semgrep | 1.172.0 | `subprocess` → JSON report |

### Blast radius

| Fault | What stops | What degrades | What is unaffected |
|---|---|---|---|
| **one absent**, `SCANNERS_REQUIRED=false` | nothing | the verdict comes from a fixture — `scan_provenance: fixture-fallback`, a **fault**, not a choice | the poisoned diff still blocks |
| **one absent**, `SCANNERS_REQUIRED=true` | **every run, clean included** — `blocking=3` | — | nothing; this is the fail-closed setting |
| **one broken** (exits non-zero, bad shebang, lost `+x`) | that run — one blocking finding per tool, severity `high` | — | `scan_provenance` stays `scanners`; the fault is visible |
| **one replaced by a different tool** | nothing | rule coverage changes | the block rule — it reads `Finding.severity`, not the tool |

The classifier in `agentorg/security/_run.py` is a **conjunction**: absent iff
`FileNotFoundError` **and** `shutil.which(argv0)` finds nothing. Either signal
alone misclassifies real cases in the **fail-open** direction — `which` misreads a
lost `+x` bit as absent, and the exception type misreads a broken shebang as
absent because errno 2 names the missing *interpreter*.

`error_finding` severity is `high`, which **is** the block threshold. Lower it to
`medium` and the lane silently reverts to failing open. It is deliberately not
`critical`, so a dead scanner does not impersonate a discovered secret in a list a
human is reading.

### What substitutability actually costs here

Replacing gitleaks means re-measuring **two line-number sets**, and this is the
one place the abstraction is not free. `tests/provenance.py` holds
`REAL_SCANNER_LINES = {3, 4}` and `FIXTURE_LINES = {4, 5}`; the two sets **overlap
at line 4**, so only the whole set separates the modes. A replacement tool that
reported the fixture's pair would destroy the discriminator while every provenance
assertion kept passing.

**Measured on this machine 2026-08-28:** local gitleaks is **8.30.1** and local
semgrep **1.173.0**, against image pins of 8.21.2 and 1.172.0. The discriminator
still comes out `{3, 4}` — so it survives nine minor versions of gitleaks, which
is genuine evidence of robustness. It is not a guarantee.

The image and CI pins **agree** at this commit, verified rather than trusted: the
Dockerfile's comment claims they match `ci.yml:124-126`, and they do. That
agreement matters because CI is what the block rule's expected findings were
measured against.

## 3 · Seam-bound — GitHub, and three AWS services

### GitHub

**One file, 1132 lines, 14 distinct API operations, and zero raw REST calls.**

```
grep -nE 'requests\.|urlopen|_requester|/repos/' agentorg/github_ops.py   -> 0 hits
```

That zero is the property that makes GitHub seam-bound rather than load-bearing: a
second integration has a **countable** target rather than an open-ended one.

| Operations | |
|---|---|
| read | `get_repo`, `get_branch`, `get_contents`, `get_pulls`, `get_issue`, `get_commit`, `get_check_runs` |
| write | `create_git_ref`, `create_file`, `update_file`, `create_pull`, `create_comment`, `merge`, `edit` |

The switch is one function: `_use_local()` returns `config.OFFLINE or not
(config.GITHUB_TOKEN and config.GITHUB_REPO)`. The offline branch does **real
git** — `init`, `checkout -B`, `add`, `commit` — not a stub.

#### Blast radius

| Change | What stops | What degrades | What is unaffected |
|---|---|---|---|
| GitHub API unavailable | nothing raises — `post_comment` returns a ref in every case and never raises | every stage comment becomes `comment://<run_id>`, meaning *not delivered*; the PR is a local branch | the pipeline runs to completion; the security verdict is unchanged |
| token loses a scope | that operation | silently — this already happened: the dispatch token lost `actions:write` on this repo and **both GitHub and the Lambda reported success** | everything else, which is what made it hard to find |
| PyGithub breaking change | **`github_ops.py` dies at import**, and `graph.py` imports it | — | nothing — this is the module-level import below |
| **the three human gates** | **the gates themselves** | — | — |

**The gates are the part that is not seam-bound.** They are GitHub Environments,
enforced by the platform rather than by our code — which is a strength (we cannot
skip them) and the single largest coupling in the system. A fully self-hosted
deployment needs its own approval mechanism. That is specification §11's UI, and
it is why §6 and §9 are sequenced together.

### The AWS services, measured

Five distinct client strings across four services:

| Service | Where | Purpose |
|---|---|---|
| `dynamodb` | `agentorg/log.py:164` | the audit trail, one of two backends |
| `bedrock-agentcore-control` | `agent_client.py:164`, `github_ops.py:1021` | list runtimes, read ARNs |
| `bedrock-agentcore` | `agent_client.py:184` | invoke a runtime |
| `events` | `infra/ingress/handler.py:128` | `PutEvents` |
| `secretsmanager` | `infra/ingress/handler.py:136` | the webhook secret |

**`bedrock-agentcore` and `bedrock-agentcore-control` are two service models of one
product**, and describing "the AgentCore client" is wrong: the data plane has
`invoke_agent_runtime` and not `list_agent_runtimes`; the control plane is the
reverse.

**Bedrock model invocation does not appear in this table**, and that absence is
the finding. It goes through `strands`, not a boto3 client — so a boto3-only
inventory would miss the single most load-bearing dependency in the system.

| Service | Blast radius if it changes |
|---|---|
| DynamoDB | **none today.** `run-pipeline.yml` sets no `STATE_BACKEND` and runs on the `local` default with an Actions artifact handoff. `STATE_BACKEND=dynamodb` is known debt — `run_stage.py:_load` calls `gates._state_path`, which refuses on that backend, so every cloud stage after `plan` raises |
| EventBridge + Lambda | the **automatic trigger** stops. A hand `gh workflow run` still works, so the pipeline is unaffected and only the ingress path is lost |
| Secrets Manager | the webhook Lambda returns **500** on every delivery — deliberately not 401, because "your signature failed" would be a lie |
| AgentCore | see §4 |

## 4 · Load-bearing — the model, pydantic, AgentCore

### The model provider

| | |
|---|---|
| References to `bedrock` | 41 case-sensitive, 81 case-insensitive (agentorg + infra) |
| Where the seam is | `agentorg/common/llm.py` — `_complete` |
| Second implementation | **exists**: `LLM_BASE_URL` routes to any OpenAI-compatible gateway, via `strands.models.openai` |

**There is no `openai` package dependency**, despite the token appearing 7 times
case-insensitively. It is reached through `strands.models.openai`. Do not list
`openai` as a dependency — that was the specification's own §5 count, and it is
the one that reproduces.

#### Blast radius — and this is the reassuring one

| Change | What stops | What degrades | What is unaffected |
|---|---|---|---|
| Bedrock unavailable, or IAM denies the call | **nothing** | every agent serves its fixture; `llm.text()` returns `None` on every failure by design | **the security verdict.** `compute_security_verdict` is pure Python over scanner output — no model, no I/O |
| Bedrock prices change | nothing | cost only | the verdict |
| the model gets worse | nothing | diff quality, revision count, prose | the verdict |

**The block rule cannot be affected by the model provider at all**, and that is
the deliberate architecture rather than a lucky property. It is also the answer to
"what is your competitive advantage": a model that can be persuaded, distracted or
prompt-injected is not the thing standing between a credential and `main`.

**The measured cost of this graceful degradation.** For about a week every agent
in the deployed pipeline answered from its fixture, with every job green, because
of three stacked IAM defects — and *nothing anywhere said the model had not
answered*. The fallback was correct behaviour; being unable to **see** it was the
defect. That is why `model_provenance` and `scan_provenance` exist, and why
`preflight.py` check 1 simulates the action the SDK actually calls rather than
reading a green apply.

### pydantic — the quietest load-bearing dependency

**5 module-level imports, 0 lazy ones:**

```
agentorg/state.py:16              agentorg/agents/server.py:47
agentorg/agents/sre.py:47         agentorg/common/agent_client.py:78
agentorg/common/llm.py:33
```

Module-level means **the importing module dies at import**. `state.py` is the
frozen contract, imported by 52 files under `agentorg/`, `tests/`, `scripts/` and
`infra/` — measured with
`grep -rl "from agentorg.state import\|from ..state import\|from .state import" ...`.
There is no fallback, no seam and no second implementation.

**pydantic is more load-bearing than AWS is**, and that is not obvious from a
reference count — `bedrock` appears 41 times and `pydantic` 19. The right metric
is import style, not frequency.

| Package | Module-level | Lazy | Blast radius |
|---|---|---|---|
| `pydantic` | **5** | 0 | the contract, the HTTP server, the remote seam and the model helper all die at import |
| `github` (PyGithub) | **1** — `github_ops.py:41` | 0 | `github_ops.py` dies, and `graph.py` imports it, so the pipeline dies |
| `boto3` | 1 — `infra/ingress/handler.py:93` | **6** | the **Lambda** dies. Every import under `agentorg/` is lazy, so the pipeline degrades rather than dying |
| `strands` | **0** | 3 | only the calling function fails; every module still imports |

That asymmetry is the inventory's most useful line: `pip uninstall boto3` degrades
this system, and `pip uninstall pydantic` ends it.

### AgentCore

Load-bearing **by choice, with the fallback already built and tested**.
`REMOTE_AGENTS` defaults to `false`, which keeps the in-process path the tested one
— the whole suite runs through `call_agent`. If the runtimes misbehave, unsetting
one variable puts the pipeline back on the path that has been green all week.

**There is no fallback to local at runtime**, deliberately: a run that silently ran
the planner in-process after failing to reach the runtime would report success for
the thing it did not do. Every failure raises, and the classifier has six classes
plus an explicit **UNCLASSIFIED** branch — because a classifier that guesses is
worse than one admitting it did not recognise the error.

## 5 · Pin tightness — the supply-chain answer

### The image: five packages, all exact

| Package | Version |
|---|---|
| `strands-agents` | `==1.52.0` |
| `bedrock-agentcore` | `==1.22.0` |
| `pydantic` | `==2.13.4` |
| `boto3` | `==1.43.75` |
| `PyGithub` | `==2.10.0` |

### A local install is not the image

`pyproject.toml`'s runtime list is largely unpinned:

| Specifier | Pin |
|---|---|
| `pydantic>=2.0` | FLOOR_ONLY |
| `strands-agents` | **UNPINNED** |
| `boto3` | **UNPINNED** |
| `PyGithub` | **UNPINNED** |
| `flask` | **UNPINNED** |

The image installs `requirements.txt` **then** `pip install --no-deps .`, so the
exact pins win inside the container. They do **not** win for a developer running
`pip install -e .[dev]`. So the environment the suite runs in locally and the
environment the image ships are **different closures**, and a CVE report against
one does not describe the other.

Three further gaps, each stated rather than discovered:

- **`bedrock-agentcore` is declared only in `requirements.txt`**, never in
  `pyproject.toml` — so a dev environment does not have it at all.
- **The ingress Lambda has no dependency file.** It imports stdlib plus boto3, and
  that boto3 comes from the AWS-provided runtime: unpinned, and AWS chooses the
  version. Acceptable for three API calls; worth stating.
- **The base image is pinned by tag, not digest** (`python:3.12-slim`). A tag is
  mutable. Pinning the digest would make a base security update require a commit
  here — a real tradeoff rather than an oversight.

Full SBOM and the scanner-update process: `sbom.md` in this directory.

## 7 · The summary a judge should get

| Dependency | Severity | If it disappeared tomorrow |
|---|---|---|
| gitleaks / trivy / semgrep | substitutable | the gate reports a **fault** and says so; the poisoned diff still blocks. Re-measuring two line-number sets is the real cost |
| GitHub API | seam-bound | one adapter, 14 operations, zero raw REST. Comments degrade to `comment://`; the verdict is unchanged |
| GitHub **Environments** | **seam-bound in name only** | **the three human gates stop existing.** The largest coupling in the system, and the reason the §11 UI and the self-hosted path are one piece of work |
| Bedrock | load-bearing, **with a working second path** | every agent serves a fixture; **the security verdict is unaffected** — it is pure Python over scanner output |
| pydantic | load-bearing, **no seam** | the contract, the server, the remote seam and the model helper die at import. The quietest and hardest dependency in the system |
| AgentCore | load-bearing **by choice** | unset `REMOTE_AGENTS` and the pipeline runs in-process, on the path the whole suite already exercises |

## 8 · PHASE 4 — twelve lanes, and the dependency set did not move

The baseline was measured at `9b2b1ee` over **31 modules**. At `d6165c8` the package
is **76 modules** — 2.5× the code, eleven packages where there were four. The
interesting number is the one that did not change.

Same AST scan, both ends, third-party imports only (stdlib and first-party excluded):

```
5215ca5   31 modules   ['boto3', 'botocore', 'github', 'pydantic', 'starlette', 'strands']
d6165c8   76 modules   ['boto3', 'botocore', 'github', 'pydantic', 'starlette', 'strands']
```

**Byte-identical sets.** Twelve lanes — a durable queue, multi-tenancy with encrypted
secrets, a scoring policy, cost instrumentation, an integration interface, retrieval, a
control-plane API and a sixth agent — added **zero** new third-party Python
dependencies to the runtime package.

That is not restraint; it is a **test doing it**.
`test_agentcore_deploy_assets.py::test_requirements_covers_every_third_party_import_in_the_package`
AST-walks `agentorg/`, so any import here becomes a pinned dependency of all five arm64
images. Three lanes hit it and each recorded the same conclusion independently:

| Lane | Wanted | Refused because |
|---|---|---|
| **H** (retrieval) | an embeddings client or a vector store | would ship a vector database to five agent containers. `search.py` is weighted token overlap instead — sets not counts, `keywords` at 3× body text, ties broken on `doc_id` |
| **K** (control plane) | `starlette` + `uvicorn`, **both already installed** | `starlette` sits in that test's `_NOT_RUNTIME` list described as "dead code today", so importing it from a live module would make the exclusion a lie. Stdlib `http.server` instead |
| **B** (tenancy) | `cryptography` for AES-GCM | absent from the declared closure — PyJWT requires it only under an extra and CI installs `.[dev]`, so it works locally and fails in CI. Stdlib encrypt-then-MAC over an HMAC-SHA256 keystream instead |

**Lane B's is the one to read twice**, because it is the only case where the refusal
cost a security property rather than convenience. The cipher is the right *shape* —
per-record random nonce, scrypt subkeys, encrypt-then-MAC — **without a reviewed
constant-time primitive.** Every row records which cipher wrote it, the way
`scan_provenance` records scanner mode, so a KMS migration would be visible in the data.
Binding it to KMS is a stated further step and is costed in `limitations.md`.

`starlette` remains the anomaly in the table above: it is imported by exactly one module
(`agentorg/common/health.py`) and was already so at the baseline. The measurement names
it rather than tidying it away.

### The coupling that DID move, and it moved the right way

```
9b2b1ee   modules touching a vendor SDK  4 of 31   MODULE-LEVEL  1
d6165c8   modules touching a vendor SDK  5 of 76   MODULE-LEVEL  2
```

| Module | Hard (module level) | Deferred (inside a function) |
|---|---|---|
| `common/agent_client.py` | — | boto3, botocore |
| `common/llm.py` | — | boto3 |
| `github_ops.py` | **github** | boto3, botocore |
| `integrations/__init__.py` | **github** | — |
| `log.py` | — | boto3 |

Vendor-touching modules went from **12.9%** of the package to **6.6%** — the
denominator grew 2.5× while the numerator grew by one. And the one new module-level
import is `integrations/__init__.py`, which is **Lane D's adapter registry**: the
module whose entire purpose is that GitHub becomes one adapter behind one interface. A
hard import there is the interface declaring what it ships, not a new coupling.

### A NEW DEPENDENCY CLASS THE BASELINE HAD NO ROW FOR — `web/`

The Phase 1 inventory covered `agentorg/` because that was all there was. `web/` is
**53 files, 8,769 lines**, and it has its own closure that none of the four Python gates
can see:

| Package | Version | Severity | Blast radius |
|---|---|---|---|
| `next` | 16.3.3 | **load-bearing** | the entire product UI. No seam; it *is* the framework |
| `react` / `react-dom` | 19.2.8 | **load-bearing** | as above |
| `next-auth` | 5.0.0-**beta**.32 | **load-bearing, and on a beta** | sign-in stops working; `POST /api/approvals` is the first surface here that can open a gate over a network, and it takes `by` from the session this package issues |
| `@auth/pg-adapter` + `pg` | 1.11.3 / 8.23.0 | **seam-bound** | sessions live in Postgres. Swappable for another adapter; the session *strategy* is not — a JWT strategy would make `DELETE /api/link/github` delete a row nothing reads while the cookie worked for 30 days |
| `typescript` / `eslint` / `vitest` | 5.9.3 / 9.39.5 / 4.1.11 | dev only | three of the four web gates. Not shipped |

**`next-auth 5.0.0-beta.32` is the sharpest single dependency fact in this document.**
A pre-release version is load-bearing for authentication on the one route in this
repository that can approve a security gate. It is named here rather than in a comment
because a beta pin is a decision with an expiry date, and nothing in the repository
tracks that date.

**And the honest limit that outranks all five rows: no Postgres has ever been
connected.** `agentorg/db/engine.py` is sqlite3-only, nothing in the suite connects to
one, and `docker compose up` has never run — so the sign-in flow these packages exist
to serve **has never completed**. The Auth.js configuration typechecks and builds;
that is a different claim, and `limitations.md` costs the difference.
