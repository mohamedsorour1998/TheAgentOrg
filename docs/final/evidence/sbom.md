## The scanner-update process

A scanner bump is not a version edit. It can move a reported line number, and this repository's entire verification story rests on two line-number sets staying distinct. Five steps, in order:

**1. Bump the version in BOTH places, in one commit**

agentorg/agents/Dockerfile (ARG <TOOL>_VERSION) and .github/workflows/ci.yml (env <TOOL>_VERSION). They are two declarations of one fact; a commit that moves one is a build whose scanner differs from the one the suite was gated against.

```
.venv-main/bin/python scripts/measure_sbom.py  # agree: true
```

**2. Re-measure the block rule's expected findings**

scripts/scan_gate.py carries EXPECTED_BLOCKING, measured on gitleaks 8.21.2. A scanner update can move a reported LINE NUMBER, and the line numbers are the only field separating a real scan from the fixture.

```
.venv-main/bin/python scripts/scan_gate.py
```

**3. Re-measure the provenance discriminator**

tests/provenance.py's REAL_SCANNER_LINES is {3, 4} and FIXTURE_LINES is {4, 5}. If an update moves the real set onto {4, 5} the discriminator is GONE and every provenance assertion keeps passing while proving nothing. The sets must stay distinct -- that is the acceptance test for a scanner bump, not a green suite.

```
.venv-main/bin/python -m pytest tests/test_provenance.py -q
```

**4. Rebuild the image and read the version tail**

the Dockerfile ends its scanner layer with `gitleaks version && trivy --version && semgrep --version`. That tail catches a binary that downloads but cannot execute -- a BROKEN scanner, which blocks every run including the clean one, and is a different fault from an absent one.

```
the deploy workflow's build step; failure is the intended outcome
```

**5. Re-run preflight against the deployed runtime**

check 3 invokes the security runtime and asserts the real line numbers. It is the only check that distinguishes a real scan from the fixture, and a runtime reports READY before its endpoint serves the new version -- so a green deploy is not evidence.

```
.venv-main/bin/python scripts/preflight.py
```

## What this SBOM cannot see

**the transitive dependency closure actually installed**

requirements.txt pins five DIRECT packages. strands-agents and boto3 pull dozens of transitive ones, and their versions are resolved at build time by pip, not declared anywhere in this repo.

```
docker run --rm --platform linux/arm64 <account>.dkr.ecr.us-east-1.amazonaws.com/theagentorg-shared-security-agent:latest pip freeze
```

**the base image's own OS package inventory**

python:3.12-slim ships a Debian userland this repo never lists.

```
syft public.ecr.aws/docker/library/python:3.12-slim -o cyclonedx-json
```

**the digest of the image actually deployed**

five ECR tags are deployed and a tag is mutable. Without a digest an SBOM describes an intention rather than an artifact.

```
aws ecr describe-images --repository-name theagentorg-shared-security-agent --region us-east-1 --query 'imageDetails[].imageDigest'
```

**known vulnerabilities in any of the above**

an SBOM is an inventory, not an assessment. trivy is already in the image and can scan the image it is in.

```
trivy image --format cyclonedx <image reference>
```
